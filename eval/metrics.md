### Why these numbers are near-perfect, and why that is not a result

The same author wrote the defect generator and the detection rules, so the main set measures whether two expressions of one set of assumptions agree with each other. They do. That is internal consistency, not capability, and it is reported here only as a regression guard.

The number worth reading is the holdout.


## Adversarial holdout

### What the holdout found

On first run it failed badly — **33.3% false clears (4 of 12)** and 33.3% false escalates. Both causes were real bugs:

1. **Phantom refunds were cleared.** The three-way ledger check compared only *payment* lines against the order ledger. A refund reduces the payout and the bank credit identically, so it always ties; a refund for an order the books never refunded was invisible to every totals-based check. Fixed by `classify.unsupported_refunds()`.

2. **Consolidated payouts with a transfer charge were escalated.** Subset-sum requires exact totals, and a Rs 23 charge broke exactness, so both payouts reported as never paid. Fixed by excluding itemised charge rows from the payout arithmetic.


### Honest caveat on the post-fix numbers

Once the engine was fixed against this holdout, the holdout stopped being unseen data — it became training data. The 0% above is therefore **not** an independent measurement. It generalises across seeds within the same compound families (table above), which is a weaker claim than generalising to compound types that have not been invented yet. A genuinely independent number needs compound families written by someone who has not read `classify.py`.


## What this file does NOT cover

Every number above comes from the **deterministic engine**. `run_eval.py` never invokes the agent layer: no API key, no network, nothing that reproduces differently on another machine. That is deliberate — these are the numbers the product stands on, and they must be checkable by anyone with a clone and an interpreter.

The agent layer was measured separately, against **Gemini** — never against Claude, because no Anthropic key was available, so that backend has met only a scripted stub whose wire shape I wrote myself. Those numbers, and the three bugs the real calls exposed, are in [`../README.md`](../README.md) and [`../docs/FAILURE_LOG.md`](../docs/FAILURE_LOG.md). They are not repeated here, because a figure needing a paid key and a vendor's uptime to reproduce does not belong beside figures that need neither.


## Known limitations

- **Sub-rupee blindness.** Differences of 5 paise or less are absorbed as fee/GST rounding, so this system cannot detect sub-rupee skimming. Deliberate: chasing 3 paise costs more than 3 paise.

- **Single-label classification.** A settlement with two defects gets one reason code. Disposition stays correct, but the explanation is partial.

- **Bank charges are recognised by narration keywords** (`CHARGE`, `COMMISSION`, `FEE`). A bank wording its fees differently would have them escalated as unexplained shortfalls — safe, but noisy. Production should match against the bank's published fee schedule.

- **Synthetic data throughout.** No real settlement report was used, and real ones are messier in ways this generator does not imagine.
